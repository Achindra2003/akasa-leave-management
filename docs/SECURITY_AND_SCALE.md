# Security & Scalability Assessment

This assessment was written after testing the live deployment (Render + Supabase Mumbai + Groq) on 2026-11-06. Every claim below comes from a test, a measurement, or a tool output. Where something is *not* done, it says so.

## 2. Security: what is in place

**Identity and access**
- Passwords are hashed with **argon2**. JWTs are HS256 with an 8-hour expiry, and the secret is **generated by Render** (`generateValue`), not stored in the repo.
- **Authorisation is enforced in the service layer**, not just in routes (defence in depth). Viewing a request you're not entitled to returns **404, not 403**, so request IDs can't be enumerated (verified in production).
- **Separation of duties is impossible to bypass:** nobody approves their own leave, nobody signs two levels of one request, and delegates act only while the approver is actually on approved leave.

**Input and files**
- Every input is validated by Pydantic; all SQL goes through the ORM's bound parameters (no string-built SQL).
- **Uploads:** the type allow-list is checked against **magic bytes**, not the client's `Content-Type` (a renamed `.exe` is rejected, verified in production). The size cap is enforced *while streaming*. Files are served only to the approval chain, with `Content-Security-Policy: sandbox`, `nosniff` and `no-store`, and **every view is audited**.

**Transport and browser**
- HTTPS with **HSTS** (1 year). A strict **CSP** (`script-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`) produced 0 violations across all screens. `X-Frame-Options: DENY`, Referrer and Permissions policies. API responses are `no-store`.
- No CSRF exposure: auth is a bearer header, not a cookie.

**Abuse**
- **Rate limits:** login allows 10 attempts per minute per IP+email (verified in production: 10×401 then 429 with `Retry-After`). LLM endpoints allow 20 per minute per user, which protects the Groq spend.

**AI-specific**
- **Least privilege:** the agent has no submit, approve or reject tool. Submission happens only in a graph node after an explicit human resume, verified live: a discarded draft creates nothing.
- Untrusted text (reasons, document contents) is delimited and schema-validated. Prompt injection via chat *and* via document text is covered by tests. The AI never sets document verification status; only humans do.

**Integrity and audit**
- The overlapping-leave guarantee is a **database exclusion constraint** (5 concurrent identical submits → exactly 1 succeeds).
- **Optimistic locking** on decisions.
- The audit log is **append-only, enforced by a DB trigger**, with a correlation ID linking every row to its request log line.

## 3. Security: known gaps (would fix before a real rollout)

| Gap | Risk | Production fix |
|---|---|---|
| **Demo mode is on**: public demo accounts with a published password, and `/auth/demo-accounts` | Anyone can sign in as HR | Set `SEED_DEMO_DATA=false` (it also disables the endpoint), and create users through HR provisioning / SSO |
| JWT in `sessionStorage`, no server-side revocation | A stolen token stays valid for up to 8 hours; XSS could read it (mitigated by the strict CSP and React escaping) | **SSO (Azure AD / Okta OIDC)**, httpOnly `Secure` `SameSite` cookie, short-lived access token + refresh, revocation on logout/offboarding |
| No MFA or account lockout | Credential stuffing (slowed by the rate limit) | Comes with SSO |
| Medical documents are **sensitive personal data** (India **DPDP Act 2023**) | Stored as Postgres `bytea`; encrypted at rest only at Supabase's disk level | Object storage with KMS encryption and short-lived signed URLs, a retention policy (e.g. delete N days after the leave ends), and a consent notice at upload |
| Leave reasons and document text go to **Groq** (a third-party processor) | Data leaves the organisation | DPA with the provider, or a self-hosted model behind the same `LLM_PROVIDER=openai_compat` switch; PII redaction before prompts |
| Audit trigger protects against the *app*, not a DB superuser | An admin could drop the trigger | A separate DB role with INSERT-only grants for the app; stream audit rows to WORM/external log storage |
| Rate limiter is in-process | Resets on deploy; not shared across instances | Redis-backed limiter behind the same interface |
| CSP allows inline *styles* | Low (needed for the coverage bars' style props) | CSS custom properties set via classes; hash-based styles |

## 4. Scalability: measured

**Environment:** Render **free** instance (0.1 CPU, 512 MB, US-Oregon by default) → Supabase **free** (Mumbai, session pooler), tested from India.

| Measurement | Before | After the fixes |
|---|---|---|
| DB round trips: approval queue / request detail / current user | 13 / 14 / 4 | **4 / 6 / 1** |
| Sequential latency: `/policy` (no DB) | 276 ms | 261 ms, which is *pure network*, India ↔ US |
| Sequential latency: approval queue | 3.78 s | **1.67 s** |
| 200 reads at 20 concurrent | p50 3.5 s, 6 req/s, **1/120 → 500** (pool exhaustion) | 7 req/s, p50 ~3.5 s, p95 4.3–4.8 s. **0 errors in ~1,000 requests across 5 runs except one unclassified 5xx in one run** (the 0.1-CPU instance queues work; latency is dominated by ~220 ms DB round trips) |

**Three production bugs found by testing the live system, all fixed:**
1. **Round-trip-bound latency.** Each query crossed the Pacific (~220 ms) because the app runs in Oregon and the DB in Mumbai. Lazy relation loading made one page about 13 sequential round trips. Fixed with JOINs, batched collections, and a lighter summary query for lists.
2. **Connection exhaustion.** Supabase's free session pooler allows **15 clients** per database (reproduced: `EMAXCONNSESSION`). The app could open 16. Fixed: the pool is sized to the plan (4+4+1), bursts queue for 10 s, and exhaustion returns a **503 with Retry-After** instead of a 500.
3. **Delegates couldn't use the co-pilot** (403). This wasn't a scaling bug, but the same production check found it.

**Is that fast enough?** For the expected load, yes. A leave system is write-light. Even if every employee in a mid-size airline (assume ~5,000) filed 4 requests a year, that's about **20,000 writes/year, under 1 per minute** on average. Reads are dominated by the notification bell (polled every 20 s). With **500 people online at once that's about 25 req/s**, and *that* is the number to design for. It's within reach of a single paid instance once co-located with the DB.

## 5. Scalability: the path from here (in order of value)

1. **Co-locate app and DB.** Move the Render service to **Singapore** (closest Render region to Supabase Mumbai). This cuts each round trip from ~220 ms to ~60 ms and is the single biggest win. Render can't change a service's region in place, so it's a one-time recreate from `render.yaml` (`region: singapore`).
2. **A paid instance** (no cold starts; real CPU) and a paid Supabase plan (larger pooler). Or use the **transaction pooler** with `prepare_threshold=None`, which multiplexes many app connections over few DB connections.
3. **Replace polling with server-sent events** for notifications, or add ETag/304 responses. This removes the dominant read load.
4. **Horizontal scale is already mostly possible:** auth is stateless JWT, and AI state lives in the *shared* Postgres checkpointer. Before running several instances, these need to move:
   - in-process background document checks → a queue worker (arq/Celery or a Postgres queue)
   - the in-memory rate limiter → Redis
   - migrations on startup → a release step (`preDeployCommand`)
   - attachments in the DB → object storage
5. **Read replicas and partitioning** aren't needed at this scale. A single Postgres primary handles orders of magnitude more than this workload. The indexes that matter already exist: the GiST index on `(employee_id, daterange)` from the exclusion constraint, plus the status, approver and notification-user indexes.

**Bottom line:** the design is *correct under concurrency* by construction (DB constraints, optimistic locking, transactional audit). Its *performance* on the free tier is limited by geography and plan limits, not by the architecture, and every limit hit in testing now degrades gracefully (queue, then 503) instead of erroring.
